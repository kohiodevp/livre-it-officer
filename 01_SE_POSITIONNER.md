# 01 — Se positionner

**Partie I — IDENTIFIER SON POSTE**

Cette partie traite du **candidat** : ce qu'il a fait, ce qu'il sait faire, ce
qu'il peut prouver, et ce qu'il lui reste à acquérir. `00_POSITIONNEMENT.md`
explique le fonctionnement du livre ; ce fichier-ci porte sur vous.

Elle est volontairement centrée sur le profil, sans anticiper le contenu
technique de la Partie II.

---

## 1. Pourquoi commencer par se positionner ?

Un IT autodidacte peut posséder une expérience importante sans disposer
spontanément du vocabulaire, de la structure ou des preuves nécessaires pour la
présenter.

Le problème n'est donc pas seulement :

> « Que sais-je faire ? »

Il faut également pouvoir répondre à quatre questions :

- Dans quel type de rôle puis-je être utile ?
- Sur quelles compétences puis-je m'appuyer ?
- Quelles expériences concrètes permettent de l'établir ?
- Qu'est-ce que je dois encore apprendre ou démontrer ?

Le positionnement professionnel n'est pas une opération de présentation destinée à
embellir un parcours. C'est une opération de **clarification**.

L'objectif est de passer d'une expérience parfois dispersée à une représentation
professionnelle lisible :

```
expérience → compétence → preuve → valeur professionnelle
```

---

## 2. Le profil de l'IT autodidacte

L'autodidacte construit souvent ses compétences dans des conditions différentes
de celles d'un parcours académique classique.

Il peut apprendre :

- à partir de problèmes réels ;
- par expérimentation ;
- par documentation ;
- par recherche autonome ;
- par répétition ;
- par résolution d'incidents ;
- dans des environnements disposant de peu de ressources ;
- sans validation institutionnelle régulière.

Cette trajectoire peut produire une expérience riche, mais elle comporte un
risque : **confondre familiarité et maîtrise**.

Avoir déjà rencontré Linux, Docker, un VPN ou un système de sauvegarde ne
signifie pas automatiquement que l'on maîtrise leur administration en production.

Le livre adopte donc une règle simple :

> **L'expérience constitue une matière première. La compétence doit être structurée
> et la preuve doit être construite.**

---

## 3. Faire son audit personnel

L'audit personnel consiste à examiner son profil sans chercher immédiatement à
le valoriser.

Pour chaque domaine, identifier :

1. ce que je connais ;
2. ce que j'ai déjà pratiqué ;
3. ce que j'ai réellement produit ;
4. ce que je peux reproduire ;
5. ce que je peux vérifier ;
6. ce que je peux expliquer ;
7. ce que je ne maîtrise pas encore.

### Exercice — Audit initial

Pour chaque compétence importante, compléter :

| Domaine | Ce que je connais | Ce que j'ai pratiqué | Preuve disponible | Ce que je peux expliquer | Ce qui reste à travailler |
|---|---|---|---|---|---|
| Systèmes | | | | | |
| Réseau | | | | | |
| Sécurité | | | | | |
| Virtualisation | | | | | |
| Conteneurs | | | | | |
| Sauvegarde | | | | | |
| Supervision | | | | | |
| Scripting | | | | | |
| Documentation | | | | | |
| Support | | | | | |

Cet exercice ne cherche pas à produire un score.

Il sert à rendre visibles les écarts entre :

```
connaissance → pratique → maîtrise → preuve
```

## 4. Ne pas sous-estimer l'expérience en environnement contraint

Une expérience acquise dans un environnement contraint peut développer des
réflexes professionnels spécifiques :

- rechercher la cause avant d'agir ;
- tenir compte des ressources disponibles ;
- anticiper les pannes ;
- limiter les dépendances ;
- documenter les procédures ;
- prévoir une solution de récupération ;
- distinguer une panne locale d'une panne réseau ;
- travailler avec une connectivité dégradée ;
- faire des choix proportionnés aux moyens disponibles.

Ces capacités peuvent être particulièrement utiles dans des environnements où
l'infrastructure informatique doit rester exploitable malgré des contraintes
opérationnelles.

Mais elles doivent être **traduites en compétences professionnelles
observables**.

Dire :

> « J'ai beaucoup travaillé dans des environnements difficiles »

est moins informatif que de pouvoir montrer :

> « Voici le problème rencontré, les contraintes disponibles, les choix
> effectués, le résultat obtenu et la preuve conservée. »

L'expérience devient alors exploitable professionnellement.

## 5. Transformer une expérience atypique en compétence lisible

Une expérience atypique ne doit ni être dissimulée ni être présentée comme une
preuve automatique de compétence.

Il faut effectuer une traduction.

### Exemple de transformation

**Expérience**

> Administration d'un environnement informatique avec ressources limitées.

↓

**Situation technique**

> Ressources CPU, mémoire, réseau ou énergie limitées.

↓

**Action**

> Diagnostic, simplification de l'architecture, automatisation ou adaptation des
> procédures.

↓

**Résultat**

> Service maintenu, procédure reproductible, incident réduit ou opération
> documentée.

↓

**Preuve**

> Script, configuration, journal, procédure, test, dépôt ou autre artefact
> vérifiable.

↓

**Compétence professionnelle**

> Capacité à administrer et maintenir un système sous contrainte.

Cette chaîne doit rester fidèle aux faits. Elle ne doit jamais transformer une
intention en résultat obtenu.

---

## 6. Construire sa proposition de valeur

La proposition de valeur répond à une question :

> **Pourquoi mon profil peut-il être utile dans le poste visé ?**

Elle ne doit pas être une accumulation de technologies.

Une formulation utile relie :

```
profil + environnement maîtrisé + problème traité + valeur apportée
```

### Canevas

> Je suis un IT autodidacte orienté vers __________________.
>
> Mon expérience m'a principalement amené à travailler sur __________________.
>
> Je suis particulièrement à l'aise lorsque __________________.
>
> J'ai développé cette capacité à travers __________________.
>
> Je peux l'étayer par __________________.
>
> Je cherche maintenant à renforcer __________________.

Le canevas doit être complété à partir de l'expérience réelle.

Une compétence non démontrée peut être présentée comme un **objectif de
progression**, mais pas comme une preuve.

---

## 7. Le récit d'origine

Le récit d'origine explique comment le candidat est arrivé à son niveau actuel.

Il ne s'agit pas d'écrire une autobiographie.

Le récit doit permettre de comprendre :

- le point de départ ;
- le déclencheur ;
- les premiers apprentissages ;
- les difficultés rencontrées ;
- les environnements dans lesquels l'expérience s'est construite ;
- les responsabilités progressivement prises ;
- les compétences développées ;
- la direction professionnelle recherchée aujourd'hui.

### Structure courte

```
Point de départ → apprentissage → confrontation au réel
               → progression → orientation actuelle
```

Le récit doit rester factuel.

Il n'est pas nécessaire de prétendre avoir suivi un parcours linéaire. Un
parcours autodidacte peut au contraire être expliqué comme une succession
d'expériences et de problèmes ayant progressivement construit une pratique.

---

## 8. Ce que l'on peut affirmer

Un principe essentiel du livre est la distinction entre plusieurs niveaux
d'affirmation.

| Statut | Définition ici | Ce qui le justifie |
|---|---|---|
| **DÉMONTRÉ** | Une preuve vérifiable, issue d'une exécution constatée, permet d'établir le fait | Un artefact d'exécution |
| **DÉCLARÉ** | Le candidat affirme avoir réalisé quelque chose, mais la preuve disponible ne permet pas encore de l'établir | Documentation, intention |
| **INTERPRÉTÉ** | Une conclusion raisonnable est tirée à partir d'éléments observés, mais elle dépasse ce qui est directement démontré | Raisonnement |
| **OBJECTIF** | La compétence est recherchée ou doit encore être développée | Plan de travail |
| **NON ÉTABLI** | Les informations disponibles ne permettent pas de conclure | Absence d'information |

Cette distinction protège le candidat.

Elle permet de dire :

> « Je l'ai pratiqué »

sans prétendre :

> « Je maîtrise cette technologie en production »

lorsque cette seconde affirmation n'est pas établie.

---

## 9. Construire son identité professionnelle

L'identité professionnelle ne se résume pas à un intitulé.

Un même autodidacte peut avoir développé des expériences en :

- administration système ;
- réseau ;
- automatisation ;
- sécurité ;
- supervision ;
- support ;
- documentation ;
- développement d'outils.

Le travail de positionnement consiste à identifier le **centre de gravité** du
parcours.

### Questions de travail

- Quels problèmes ai-je le plus souvent résolus ?
- Quels environnements ai-je le plus souvent administrés ?
- Quelles tâches puis-je refaire sans repartir de zéro ?
- Quelles compétences apparaissent dans plusieurs expériences ?
- Quels domaines dois-je encore renforcer ?
- Quels artefacts permettent de montrer mon travail ?
- Quel type de responsabilité suis-je prêt à assumer ?

Le positionnement final doit être suffisamment précis pour être crédible et
suffisamment honnête pour rester défendable.

---

## 10. Positionnement et preuves

Le positionnement prépare directement le travail des parties suivantes.

Une compétence annoncée devra progressivement être reliée à une preuve.

La chaîne de référence est :

| Temps | Ce qu'il faut |
|---|---|
| **POSITIONNEMENT** | Ce que je prétends pouvoir apporter |
| **COMPÉTENCE** | Ce que je dois savoir faire |
| **PRATIQUE** | Ce que je réalise |
| **VÉRIFICATION** | Comment je sais que cela fonctionne |
| **PREUVE** | Ce que je peux montrer |
| **EXPLICATION** | Comment je peux le défendre professionnellement |

Cette chaîne constitue le passage entre l'expérience personnelle et la
professionnalisation.

### Mes limites

- Qu'est-ce que je ne maîtrise pas encore ?
- Quelles compétences dois-je approfondir ?
- Quelles preuves dois-je encore produire ?

## 12. Résultat attendu

Le résultat de cette partie n'est pas un discours parfait.

C'est une **carte honnête du candidat**.

À la fin de l'exercice, le lecteur doit pouvoir distinguer :

- son expérience ;
- ses compétences ;
- ses preuves ;
- ses objectifs ;
- ses limites ;
- la valeur professionnelle qu'il souhaite apporter.

Cette clarification permet ensuite d'aborder le socle technique avec une question
différente :

> **Que dois-je maintenant savoir faire, pratiquer et démontrer ?**

## 13. Ce que devient cette carte

La partie s'achève sur des cases à remplir. Ce n'est pas une fin : c'est une
matière première.

Les quatre canevas que vous venez de remplir constituent une **carte
d'inventaire** :

- la proposition de valeur dit ce que vous prétendez pouvoir apporter ;
- le récit d'origine dit d'où viennent vos compétences ;
- le centre de gravité dit sur quoi elles s'appuient réellement ;
- les limites déclarées disent ce qui n'est pas encore acquis.

Cette carte a une conséquence qu'il faut assumer : **elle énonce, sans les
démontrer, des compétences que vous n'avez peut-être jamais vérifiées en
conditions réelles.** C'est pourquoi elle ne peut pas être la fin du parcours.

Une compétence affirmée dans un canevas reste une affirmation. Pour qu'elle
devienne une compétence vérifiable, il faut construire le socle qui permet de la
pratiquer, puis un contexte dans lequel la pratiquer réellement — pas dans une
salle de cours, mais sur un système dont on dépend.

C'est exactement ce qu'apporte la partie suivante.

## 14. Passer à la pratique — Ce que la partie II apporte

Le positionnement personnel ne reste pas un exercice introspectif. **Il fournit
les compétences à mettre à l'épreuve dans le socle technique.**

La Partie II ne répète pas ce que vous venez d'écrire sur vous-même. Elle prend
votre inventaire et le confronte à une méthode de travail.

Concrètement, elle ajoute trois choses que la présente partie ne contient pas.

**Un socle de connaissances.** Vous avez listé des domaines — réseau, sécurité,
sauvegarde, scripting. La Partie II en donne les **quatre couches**
(matériel → système → services → utilisateur), puis traite chacun selon la même
structure : comprendre, pratiquer, vérifier, produire une preuve.

**Un cadre de travail réutilisable.** Le **cahier de laboratoire** (§ 19) est
l'instrument qui transforme une manipulation ponctuelle en expérience
exploitable. C'est lui qui portera toutes les preuves que vous construirez dans
les parties suivantes.

**Une méthode de diagnostic** (§ 16) qui vaut pour tout incident : observer,
décrire, isoler, formuler une hypothèse, vérifier, agir, vérifier à nouveau,
documenter. Elle est réutilisable bien au-delà de ce livre.

### Ce qui change concrètement

À la fin de la Partie I, vous avez un inventaire.

À la fin de la Partie II, vous aurez pour la première fois un **système avec une
méthode** — et surtout, des exercices réellement exécutés dans
l'environnement de laboratoire que vous aurez choisi.

C'est cette différence qui rendra possible la Partie III : travailler sous
contrainte n'a de sens qu'une fois la méthode de base maîtrisée.
